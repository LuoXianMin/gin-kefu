## 二、消息链路 QPS 压测

### 方法
- 60 个 bench 访客账号（商户后台批量建号，幂等），每人独立会话 + 独立 WS 订阅观察者。
- HTTP 并发池 200；`clientMsgId` 全局唯一避开幂等命中。
- 每账号消息数控制在路由级限流额度内（60/min/账号）；`BENCH_RAW=1` 模式在发送期间以守护循环清除限流键，解除业务限流测基础设施容量（仅压测环境手段）。
- 指标：发送侧成功数/QPS/HTTP 延迟分布；接收侧 WS 送达数/送达率/端到端延迟（ack 记发送时刻，WS 到达记接收时刻）/排空时间；并行 `docker stats` 采样。

### 四轮数据

| 轮 | 配置 | 成功/总数 | 时长 | 聚合 QPS | HTTP P50/P95/P99 (ms) | WS 送达率 | E2E P50/P95/P99 (ms) | 失败原因 |
|---|---|---|---|---|---|---|---|---|
| R1 | 30 账号×55，默认限流 | 1650/1650 | 1.52s | **1086** | 142/413/650 | 100% | 121/393/624 | 无 |
| R2 | 60×55（30 账号与 R1 窗口重叠）| 1796/3300 | 1.0s | 1787* | 43/142/207 | 100%* | 59/162/208 | 1504 条为老账号限流拒绝（预期保护）|
| R3 | RAW 30×100 | 1861/3000 | 1.97s | 946 | 83/383/493 | 100%* | 84/311/402 | 1132 限流 + 7 "会话不存在或无权访问" |
| R4 | RAW 60×150 | 3897/9000 | 3.57s | **1093** | 39/270/381 (max 445) | 100%* | 84/311/402 (max 442) | 5103 限流（清键周期跟不上瞬时 burst）|

*R2/R3/R4 的失败全部为服务端限流拒绝（非超时/5xx），成功消息的 WS 送达率均为 100%，无一条丢失；"排空"（发送停止后积压消费完）四轮均 ≤1s。

### 资源占用（R4 高压期 docker stats 峰值，CPU 为多核口径）

| 容器 | 峰值 CPU | 判读 |
|---|---|---|
| gva-pgsql | **248%** | 主要承载者之一：消息链路上的会话更新/幂等/审计等小事务 |
| gva-server | **218%** | 主要承载者：同步路径（鉴权/校验/Redis SetNX/Kafka produce/写库）|
| gva-kafka | 87% | 单 broker 单分区 produce 已接近饱和 |
| gva-storage-worker | 28% | 异步落库远未饱和 |
| gva-redis | 19% | 非瓶颈 |
| gva-ws-gateway | 9.5% | 推送侧远未饱和（3897 并发在途仍 <10%）|

### 瓶颈结论（按出现顺序）

1. **业务限流是第一道天花板（设计使然）**：访客发消息 60/min/账号、客服 120/min 的固定窗口。
2. 单账号 burst 超 60 即被拒（R2/R4 大量拒绝即证据）；聚合吞吐 ≈ 活跃账号数 × 窗口内额度。对真实客服场景（人是限速器）此设计合理，容量规划应按"并发账号数"而非全局 QPS 上限。
2. **解除限流后，同步发送路径实测稳定在 ~1100 msg/s**：此时 gva-server 与 pgsql CPU 同时抬升（>200%），Kafka 单 broker 87% 逼近上限——瓶颈为 **server 同步处理 + pgsql 小事务写 + Kafka 单分区 produce** 三者叠加；redis/worker/gateway 均有大量余量。
3. **接收侧（WS 推送）不是瓶颈**：数千条在途 100% 送达、排空 ≤1s、gateway CPU <10%；端到端延迟在 ~1100 msg/s 压力下 P99 ≤ 650ms。
4. 观察项（未复现）：R3 中 7 条 `code7:会话不存在或无权访问`，疑似 CreateOrResume 并发建会话竞态；R1/R2/R4 未出现，建议后续针对性并发测试确认。

### 延迟分层观察
- 低压力（R1 前置单消息冒烟）：HTTP ~39ms、端到端 ~42ms（即 Kafka→worker→gateway 全链路固有延迟约 40-80ms）。
- 高压力（R4）：P50 从 39→84ms 漂移平缓，P99 ≤ 402ms，无长尾雪崩——限流拒绝"快速失败"对整体延迟反而有保护作用。

### 扩容与优化建议
1. 提升消息限流额度前，先做以下三件事，否则瓶颈依次现形：
   - **server 水平扩容**（无状态，令牌自包含，可直接多副本 + LB）；
   - **Kafka 分区扩容**（消息 topic 当前单机单分区，acks=all 下单分区吞吐受限）+ producer 批量/linger 配置；
   - **pgsql 写路径合并**（会话 seq 更新、审计、幂等可批量化；或消息计数走 Redis 已实现，保持）。
2. 若需单机冲更高：CsRateLimit 的 Redis Incr 与消息幂等 SetNX 可 pipeline 合并；发送接口内 Kafka produce 可改异步回调 + 本地缓冲（需权衡 acks=all 语义，产品确认后再动）。
3. 待补测：WS 连接规模（5k+ 连接同会话扇出）、图片消息压测（含扫描链路）、多轮"待接入→转接"完整业务压测。

## 四、局限性声明（如实）

- 压测客户端为单进程 fetch 池，与全部容器同机运行，客户端自身与服务端存在 CPU 竞争，绝对数字偏保守。
- 未使用 wrk/k6 等专业工具；`BENCH_RAW` 清限流键为压测环境手段，禁止照搬到生产。
- 压测产生 15k+ 条 bench 消息（Mongo/pgsql 内），演示环境如需还原需手工清理。
- Docker Desktop 资源配额未固定，跨轮次数字存在 ±20% 波动。
